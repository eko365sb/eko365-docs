Cowork e Routines — guida operativa EKO365

Documento operativo che raccoglie tutto il know-how Anthropic Claude Code, Cowork desktop e Routines cloud applicato all'infrastruttura EKO365 BlueTeam.

Contesto

EKO365 BlueTeam usa tre prodotti distinti della famiglia Claude — Claude Code (CLI), Cowork (desktop app) e Routines (cloud automation) — costruiti tutti sopra Claude Agent SDK ma con casi d'uso, runtime e UI differenti. Confonderli porta a errori architetturali, ad esempio trattare una Routine come un Managed Agent o assumere che un SessionStart hook funzioni in claude.ai web.

Questa guida è la sintesi operativa di quanto validato in produzione sul ciclo M1-M4 del plugin BlueTeam, con il loop orario di Argentino (agente autonomo SOC) attivo come Routine cloud e il plugin distribuito al team via Org Settings claude.ai.

Nota
Le sezioni seguono lo stesso ordine del file sorgente docs/operations/cowork-and-routines.md nel repo EKO365-BlueTeam. La pagina è pubblicata anche su eko365sb.github.io/eko365-docs/cowork-routines/ per consultazione senza clone.

Come leggere questa guida

  • Sezioni 01-02: concetti — distinzione tra prodotti e architettura BlueTeam in produzione
  • Sezioni 03-04: dettagli runtime per Cowork desktop e Routines cloud
  • Sezioni 05-06: distribuzione plugin via Org Settings e configurazione Environment
  • Sezioni 07-09: lessons learned dai 4 incident reali, procedure operative e riferimenti

Terminal CLI per developer interactive. Esecuzione sul PC dell'operatore, full local tools, permission prompts user-scoped. Plugin support attivo via marketplace.

EKO365 Internal Docs › Cowork desktop

Cowork desktop — dettagli

App desktop nativa per knowledge worker. Esecuzione locale, plugin support, ideale per operatori SOC.

Caratteristiche

  • App desktop nativa macOS/Windows scaricabile da claude.ai
  • Stesso formato plugin di Claude Code CLI: .claude-plugin/plugin.json + skills/hooks/MCP servers
  • Plugin distribuiti via marketplace o tramite Org Settings (vedi sezione Distribuzione)
  • Esecuzione locale sul PC dell'operatore, non cloud

Vincoli importanti

Attenzione
SessionStart hook NON funziona in claude.ai web puro — solo in Cowork desktop o Claude Code CLI. Plugin self-contained con bootstrap Python embedded richiede quindi Cowork desktop installato, non il browser.
  • MCP server gira sul PC dell'utente — l'egress di rete passa via proxy Anthropic (range IP whitelistato)
  • Plugin auto-installed se l'organizzazione ha attivato l'auto-install in Org Settings; altrimenti opt-in da parte del member
  • Update plugin: il client Cowork sincronizza automaticamente le nuove version pubblicate su marketplace.json

Quando usare Cowork desktop

Per operatori SOC EKO365 (Fabio, Ilaria, futuri operatori) Cowork desktop è il client raccomandato. Permette:

  • Invocazione skill BlueTeam con comandi slash (es. /blueteam:morning-checklist)
  • Bootstrap Python embedded del plugin via SessionStart hook (impossibile in web)
  • Accesso a MCP server blueteam in locale, con autenticazione operator-scoped
EKO365 Internal Docs › Routines cloud

Routines — automation cloud Anthropic

Feature ufficiale Claude Code v2.1.72+. Configurazione cloud per agenti unattended schedulati.

Definizione

Una Routine cloud è composta da:

  • Prompt (Instructions) — istruzioni testuali al Claude agent
  • Repository GitHub — fresh clone ad ogni run
  • Environment — entità separata con env vars + setup script
  • MCP connectors — opzionali
  • Trigger — schedule cron-like, API webhook /fire, GitHub events

URL UI: claude.ai/code/routines

Sandbox di esecuzione

  • bubblewrap per isolamento filesystem
  • socat per network egress proxato (domain allowlist)
  • VM cloud isolate, credenziali (git creds, signing keys) NON nel sandbox
  • Filesystem effimero per session, ma con snapshot caching (vedi Environment)
  • uv installato automaticamente per Python interpreter management
  • Python sandbox è Debian-based — alcuni pacchetti Python sono apt-installed con potenziali conflitti pip

Daily run cap per piano

PianoRun/giornoNote
Pro5Single user
Max15Heavy individual user
Team / Enterprise25Configurazione EKO365
Nota
I Run now manuali NON contano contro il cap. Utile per debug e manual replay senza erodere il budget orario.

API trigger /fire (opzionale)

Endpoint webhook per trigger esterni:

POST https://api.anthropic.com/v1/claude_code/routines/trig_<id>/fire

Plugin distribution via Org Settings — pattern monorepo

Il marketplace EKO365 (eko365sb/claude-plugins) ospita più plugin in un monorepo distribuito al team via UI claude.ai.

Il file marketplace.json (TOC del marketplace)

File eko365sb/claude-plugins/.claude-plugin/marketplace.json — esempio strutturale:

{
  "name": "eko365-plugins",
  "owner": { "name": "EKO365 S.B. S.r.l.", "email": "info@eko365.it" },
  "metadata": {
    "description": "EKO365 private plugin marketplace",
    "version": "1.0.0",
    "pluginRoot": "./plugins"
  },
  "plugins": [
    {
      "name": "blueteam",
      "source": "./plugins/blueteam",
      "description": "...",
      "version": "1.0.0",
      "keywords": ["soc", "security", "blueteam", "..."],
      "category": "security"
    },
    {
      "name": "ekodocs",
      "source": "./plugins/ekodocs",
      "...": "..."
    }
  ]
}

Procedura admin per Sync from GitHub

1
Apri Org Settings
Vai a claude.ai → Settings → Organization → Plugins → Sync from GitHub.
2
Seleziona repository
Repository: eko365sb/claude-plugins (privato — la UI mostra solo private/internal).
3
Marketplace name
Auto-derivato dal nome del repository.
4
Sync automatically: ON
Propaga ogni push su main al team. Senza questo flag, l'admin deve triggerare sync manualmente.
5
Default access
Available (member opt-in) o Auto-install (force-install per tutti i member).
6
Save
I plugin del monorepo dichiarati in marketplace.json sono ora disponibili a tutti i member del team. Il subpath è gestito automaticamente dal manifest.

Aggiungere un nuovo plugin al marketplace EKO365

  1. Crea sottocartella plugins/<nome>/ nel repo claude-plugins
  2. Aggiungi .claude-plugin/plugin.json per quel plugin
  3. Aggiungi entry nel marketplace.json al root del repo: 
    { "name": "<nome>", "source": "./plugins/<nome>", "description": "...", "version": "1.0.0", ... }
  4. PR + merge su main
  5. Auto-sync propaga il nuovo plugin agli utenti del team

Bump version di un plugin

  1. Edita plugins/<nome>/.claude-plugin/plugin.json con la nuova version
  2. Anche marketplace.json al root deve avere la stessa version per il TOC
  3. PR + merge → sync propaga
Importante
Se la version nel plugin.json e nel marketplace.json divergono, il sync può silenziosamente non aggiornare il client. Tieni i due numeri sempre allineati.
EKO365 Internal Docs › Environment per Routines

Configurazione Environment per Routines

L'Environment è entità separata dalla Routine. Una Routine seleziona un Environment al momento della creazione.

Cosa contiene un Environment

  • Connectors — MCP server URLs, opzionali
  • Environment variables — env vars + secrets
  • Setup script — bash, eseguito pre-session
  • Domain allowlist — egress whitelisting

Setup script — comportamento cache

Pattern di caching validato empiricamente 2026-05-06:

  • Setup script content invariato → snapshot riusato → setup script NON re-eseguito → benefici cache massimi
  • Setup script content modificato → snapshot invalidato → setup re-eseguito da zero
  • Cambi al codice del repo (file Python esistenti modificati) → fresh clone è sempre fatto → editable install vede dinamicamente i file → non serve toccare il setup script
Eccezione
Se il refactor aggiunge nuovi sottomoduli al package, l'editable metadata cached potrebbe non risolverli. Mitigazione: bumpare un piccolo cambio nel setup script (es. echo aggiunto) per invalidare cache una volta. NON usare --force-reinstall ad ogni run per default — distrugge il cache benefit.

Setup script raccomandato (cache-friendly)

#!/bin/bash
set -ex

# Find repo root via pyproject.toml
REPO=$(find / -maxdepth 6 -name pyproject.toml -path '*EKO365-BlueTeam*' 2>/dev/null | head -1)
if [ -z "$REPO" ]; then
  echo 'pyproject.toml non trovato'
  exit 1
fi
cd "$(dirname "$REPO")"

# Audit log: stampa il commit clonato per debug
echo "Repo HEAD: $(git rev-parse --short HEAD) — $(git log -1 --format='%s')"

# Bypass Debian-managed PyJWT (apt-installed, no RECORD file)
pip3 install --break-system-packages --quiet --ignore-installed PyJWT

# Editable install — cache-friendly
pip3 install --break-system-packages --quiet -e .

echo "Setup OK: commit $(git rev-parse --short HEAD)"

Setup script defensivo (con --force-reinstall)

Variante usata in produzione su Argentino. Aggiunge ~5-10s/run ma è auto-robust per refactor del package:

# (... stesso preambolo ...)

pip3 install --break-system-packages --quiet --ignore-installed PyJWT
pip3 install --break-system-packages --quiet --force-reinstall --no-deps -e .
pip3 install --break-system-packages --quiet -e .

echo "Setup OK: ..."

Vantaggio: ogni run ricrea i metadata editable, vedendo automaticamente nuovi sottomoduli. Trade-off: 5-10s extra/run, trascurabile per loop orario.

Plus flag "also include default list of common package managers" → ON. Questo whitelista automaticamente i registry pubblici (pypi.org, github.com, npm, ecc.) necessari per pip install e git clone nel setup script.

Failure mode
Errore 403 Forbidden — host not in allowlist quando un dominio non è whitelistato. Errore lato socat proxy, NON lato HTTP server target.

Aggiungere un dominio all'allowlist

  1. UI claude.ai → Settings → Organization → Environments → seleziona Environment
  2. Sezione "Allowed domains" → aggiungi dominio (senza protocol)
  3. Save

Effetto immediato sulle prossime run.

EKO365 Internal Docs › Lessons learned

Lessons learned (incident log)

I 4 incident reali validati 2026-05-06 con sintomo, causa e fix per ognuno.

INCIDENT 7.1
pip install conflitti con pacchetti Debian (sandbox Routine)
Sintomo
ERROR: Cannot uninstall PyJWT 2.7.0, RECORD file not found. Hint: The package was installed by debian.
Causa
Il sandbox Anthropic Routine è Debian-based. Alcuni pacchetti Python sono apt-installed (no RECORD file pip), e pip install non li può uninstall/upgrade.
Fix
Aggiungere pip3 install --break-system-packages --ignore-installed PyJWT PRIMA del pip install -e . principale. Variante più aggressiva se altri pacchetti Debian-managed danno problema: 
pip3 install --break-system-packages --ignore-installed -e .
INCIDENT 7.2
Refactor Python package: import lazy/indented missed da sed bulk
Sintomo
ModuleNotFoundError: No module named 'X' a runtime, anche se il refactor sembra completo.
Causa
I from X import Y lazy (dentro a funzioni, indentati) NON sono matchati da sed -E '^from X ' ancorato a inizio riga. Plus i submoduli aggiunti DOPO l'editable install possono avere metadata stale.
Fix
Sed senza anchor (s|from X |from new.path |g) + smoke test exhaustive che importa esplicitamente OGNI modulo del package post-refactor: 
import importlib
modules = ['package.X', 'package.Y', ...]  # tutti
for m in modules:
    importlib.import_module(m)
INCIDENT 7.3
Cache routine snapshot e propagazione fix
Sintomo
Fix mergeato in main, ma sandbox Routine continua ad eseguire codice pre-fix.
Causa
Snapshot routine cache include filesystem post-setup. Setup script invariato → snapshot riusato → fresh clone OK ma metadata editable può essere stale.
Fix
Mitigation 1: cambiare contenuto del setup script (es. aggiungere echo) invalida lo snapshot e forza re-setup completo.
Mitigation 2 — defensiva: usare --force-reinstall --no-deps -e . nel setup, costa 5-10s/run ma garantisce metadata sempre aggiornati.
INCIDENT 7.4
Vault non raggiungibile dal sandbox Routine
Sintomo
Vault backend not available; using .env values only. (403 Forbidden host not in allowlist).
Causa
Dominio vault.bitwarden.eu non nell'allowlist Environment.
Fix
Aggiungerlo all'allowlist (vedi sezione Environment).

Pattern soft-migration secrets: tieni i 13 secrets cleartext come env vars + aggiungi BW_ACCESS_TOKEN / BW_ORGANIZATION_ID / EKO365_SECRETS_BACKEND=bitwarden. Il secrets_loader carica dal vault con priorità, fallback automatico ai cleartext se vault unreachable. Cleanup dei 13 cleartext solo dopo 24-48h di run consecutive con vault verde.
EKO365 Internal Docs › Procedure operative

Procedure operative

Sei procedure step-by-step per le operazioni più frequenti.

8.1 — Creare una nuova Routine

  1. Vai a claude.ai/code/routines → New routine
  2. Compila:
    • Name — descrittivo (es. EKO365 SmartBackup Daily Report)
    • Repository — GitHub repo collegato (es. eko365sb/smartbackup-reports)
    • Environment — seleziona o crea (vedi 8.2)
    • Trigger — schedule (cron-like UI), API webhook, o GitHub event
    • Instructions — prompt per Claude agent (markdown supportato)
  3. Save → routine attiva, primo run sul prossimo schedule (o trigger manuale "Run now")

8.2 — Creare un nuovo Environment

  1. claude.ai/code/routines → Settings (icon) → Environments → New
  2. Compila:
    • Name (es. EKO365 SmartBackup)
    • Allowed domains — lista, vedi sezione Environment
    • Setup script — bash, vedi pattern in sezione Environment
    • Environment variables — key=value
  3. Save → riusabile da N routine

8.3 — Aggiungere un nuovo plugin al marketplace EKO365

Vedi sezione Plugin Org Settings — Aggiungere un nuovo plugin.

8.4 — Bumpare un plugin esistente

Vedi sezione Plugin Org Settings — Bump version di un plugin.

8.5 — Onboarding nuovo operatore SOC

  1. Generare token Bitwarden personale (admin): 
    cd ~/claude-workspace/EKO365-BlueTeam
source ~/.eko365/bitwarden_config.env
python3 scripts/bootstrap_vault.py --new-operator-token "<nome>"
    Segui le istruzioni stampate (UI Bitwarden EU → machine account + project access + access token).
  2. Inviare token via Bitwarden Send (canale sicuro): link expiring + password. Mai email/Slack/Teams cleartext.
  3. Setup operatore (lato lui/lei):
    • Installare Cowork desktop
    • Login con account Anthropic team EKO365
    • Plugin blueteam già disponibile (Org Settings auto-distribution)
    • Lanciare /blueteam:setup → incollare token (input nascosto)
    • Verifica: /blueteam:morning-checklist → output OK

8.6 — Migration secrets di un agente al vault Bitwarden

Pattern soft (validato Argentino M4):

  1. Generare machine account dedicato nel vault con scope project
  2. Aggiungere 3 env vars all'Environment dell'agente (sostituire i placeholder): 
    EKO365_SECRETS_BACKEND=bitwarden
BW_ACCESS_TOKEN=PLACEHOLDER_paste_your_machine_account_token_here
BW_ORGANIZATION_ID=PLACEHOLDER_eko365_org_uuid
  3. NON rimuovere i secrets cleartext esistenti (fallback)
  4. Verificare allowlist contenga vault.bitwarden.eu
  5. Run now → verifica log:
    • Loaded 13 secrets from BitwardenBackend (vault OK)
    • Vault backend not available; using .env values only. (fallback attivo)
  6. Monitorare 24-48h di run consecutive
  7. Solo se tutti verdi vault → rimuovere i cleartext dall'Environment
