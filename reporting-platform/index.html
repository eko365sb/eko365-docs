Cos'è SmartReporting

SmartReporting è la piattaforma di reportistica automatizzata MSSP di EKO365. Raccoglie dati operativi e di sicurezza da decine di sistemi (Microsoft 365, infrastrutture on-premise, backup cloud e on-prem, ticketing, patch management), li aggrega per cliente e produce mensilmente e trimestralmente i report contrattuali che documentano la qualità dei servizi erogati e la conformità alle normative applicabili.

L'origine è il regolamento europeo DORA (UE 2022/2554, in vigore dal 17 gennaio 2025): le entità finanziarie devono dimostrare alle autorità di vigilanza che i propri fornitori ICT operano con standard documentati. Per Kryalos SGR (cliente EKO365 e SGR vigilata da Banca d'Italia) questo significa rendiconti periodici, strutturati, prodotti senza intervento manuale. La piattaforma è stata estesa a tutti i clienti MSSP per ottenere uniformità di servizio e poter rispondere rapidamente a richieste analoghe (NIS2, audit interni, valutazioni contrattuali).

Principi architetturali

  • Disaccoppiamento pipeline ↔ supervisor via manifest contract: ogni run scrive s3://eko365-pipelines/_runs/<pipeline>/<periodo>/manifest.json. Il supervisor li legge senza chiamare nessuna pipeline.
  • S3 come fonte di verità (decisione architetturale 2026-05-15). Niente cache locale come fonte primaria; ogni rigenerazione parte da S3.
  • Silent on success, alert on failure: la pipeline non invia nulla quando funziona; una mail dedicata parte solo se fallisce. Il digest mensile aggregato lo invia il supervisor.
  • Idempotenza: re-run di un periodo storico è sicuro (overwrite manifest e report S3).
  • Naming convention deliverabili: <Pipeline>_<EXT|INT>_<CLIENT>_<periodo>.<ext> consente discovery automatica e popolamento manifest senza enumerazione manuale.

Layout S3

Bucket Wasabi eko365-pipelines (region eu-south-1). Post migrazione del 14-15 maggio 2026 lo schema è duale: 

s3://eko365-pipelines/
├── _runs/                                # Manifest contract (supervisor input)
│   └── <pipeline>/<YYYY-MM>/
│       └── manifest.json                 # 7 manifest/mese (6 monthly + 1 quarterly)
│
├── smartreporting/pipelines/             # Pipeline-rooted (smartdesk, smartbackup, veeam, smartpatch parte)
│   └── <pipeline>/{snapshots,analysis,reports}/
│
├── <CLIENT>/                            # Tenant-rooted (smart365, smartpatch raw)
│   ├── raw/<module>/                    # Raw collected data per modulo (graph, action1, ...)
│   ├── kpi/                              # KPI calcolati (snapshot point-in-time)
│   └── exports/                          # DORA canonical exports (schema dora_kpis_v1)
│       └── dora_<service>.json           # Fonte autoritativa per dora-consolidated
│
└── infra/<CLIENT>/                       # SmartInfra legacy path (mantenuto come fallback)
Path canonical vs legacy · Il collector di dora-consolidated cerca i DORA export in tre candidate path in ordine: tenant-rooted (<CLIENT>/exports/), smartinfra legacy (infra/<CLIENT>/exports/), smartbackup legacy (smartreporting/pipelines/smartbackup/analysis/exports/<CLIENT>/). Le pipeline nuove producono sul path canonical; quelle storiche restano sul legacy ma sono ugualmente risolte.

Manifest contract

Ogni pipeline, al termine del run, scrive un manifest JSON che dichiara il proprio stato. Il supervisor cerca questi file in un percorso prevedibile, senza dipendenza diretta dal workflow.

CampoSignificato
pipelineIdentificativo univoco (smart365, smartbackup, veeam, smartpatch, smartdesk, smartinfra, dora-consolidated)
period / period_typeYYYY-MM e tipo (monthly | quarterly)
statussuccess | partial | failed
clients_processedLista tenant code effettivamente elaborati (es. ["KSGR", "DLPHRC", "SACMAR"])
reportsArray con metadata di ogni deliverable: client, type, format, filename, s3_key, size_bytes
github_run_id / _urlRun GitHub Actions associato (per audit trail)

Dettagli schema completo: manifest-contract.md

Modello di autenticazione Microsoft 365

Tutti gli script che colpiscono Microsoft 365 (Smart365, BlueTeam, EKO365-Auth) condividono un'unica app registration multi-tenant nel partner tenant EKO365, con admin consent granted su ogni customer tenant via GDAP (Granular Delegated Admin Privileges). Non esistono app diverse per progetto.

OBO account & GDAP

L'account admin-fs@eko365sb.onmicrosoft.com autentica via GDAP per operare sui customer tenant senza richiedere admin locale. Il refresh token v2.0 ottenuto non è scope-bound: cambiando lo scope nella richiesta si ottiene access token per Graph, Exchange o Security & Compliance.

Pattern di esecuzione (multi-tenant loop)

Per chiamate massive (es. interrogare tutti i tenant in sequenza) il pattern obbligatorio è REST API diretto + refresh token. Mai Connect-ExchangeOnline o Connect-MgGraph in loop: ogni connessione interattiva sarebbe un disastro di prompt e cache locali. Il refresh token si auto-rinnova ad ogni uso (validità ~90 giorni).

Aggiunta nuovi scope · La procedura è documentata: admin consent v2.0 "by-scope" per il partner tenant, poi fan-out programmatico ai customer tenant via oauth2PermissionGrants. Nessun device-code flow, nessun browser-popup per ogni cliente. Esempio in Add-ThreatHuntingPermission.ps1.

Egress & vincoli di rete

L'agente Claude Code lavora da un container con un range IP che Cloudflare WAF blocca su diversi provider (MailerSend, SaaS Alerts). Manifest writer centralizzato

La scrittura del manifest contract è un'unica CLI esposta da eko365-pipeline-core: 

python -m eko365_pipeline_core.runs write-manifest \
  --pipeline smart365 \
  --period 2026-04 \
  --period-type monthly \
  --s3-prefix smartreporting/pipelines/m365-graph/reports/mensili/2026-04 \
  --reports-dir reports/output \
  --clients-processed "C2P DLPHRC KSGR ..."

I deliverable per cliente vengono scoperti automaticamente dal naming <Pipeline>_<TYPE>_<CLIENT>_<periodo>.<ext>; per report aggregati cross-tenant (CLIENT=ALL) il flag --clients-processed permette di tracciare comunque i tenant nel manifest.

Audit, drift detection & CI hygiene

Tre meccanismi attivi prevengono drift cross-repo:

  • audit-pipeline-standard.py in pipeline-workflows/scripts: regola MS-001 verifica che ogni pipeline definita abbia uno step metrics-store; regole S3-001…005 con --check-s3 confrontano il bucket attuale con la config attesa (drift detection).
  • Contract test post-merge: dopo modifiche cross-repo (es. cambio CLI di pipeline-core), workflow_dispatch su ogni caller per verificare che il consumer abbia adottato la nuova versione (lezione catturata 2026-05-23 in feedback_contract_test_post_merge).
  • Verification 4-layer riproducibile su periodo storico: L1 audit copertura S3, L2 re-run skip-analysis, L3 plausibilità AI (Haiku), L4 full re-run opzionale. Procedura documentata in docs/.
